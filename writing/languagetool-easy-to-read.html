[02] Tools READI 2024

A spell-checker, but for Easy-to-Read

Most Spanish text-simplification tools do not run any more. So we built ours on something that already does, and taught it when to stay quiet.

In a previous study we found that asking a language model to produce Lectura Fácil does not work well enough to trust. The obvious next question is what does. If full automation fails, can a tool at least make the human adaptor faster?

That question has been asked before. Surveying what already exists for Spanish, we found a long list of projects, but a short list of things you can actually use today.

This is a recurring problem in the field, not bad luck. Research tools are built to support a paper, demonstrated, and then stop being maintained when the funding ends. The code may survive; the running service rarely does.

So rather than build another standalone prototype, we built on LanguageTool, an open-source, multilingual proofreader supporting 30 languages, already integrated into browsers and office software, with an active community maintaining it. We wrote Lectura Fácil rules for it and wrapped the result in an authoring interface we call LFWriteAssist.

Rules that know their own limits

LanguageTool rules are XML patterns. A rule matches some text, explains what is wrong, and optionally offers a replacement. That optional part turned out to be the most interesting design decision in the whole tool.

When a rule includes a suggestion, the tool can fix the text itself. When it does not, the tool can only point. We had to decide, rule by rule, which kind each one was.

We withheld the suggestion in three situations: when a correction needs context the tool cannot see; when LanguageTool’s pattern syntax cannot express the fix cleanly; and when the passage really needs rewriting rather than patching, where a piecemeal correction would damage the flow.

A tool that always answers is less useful than one that knows when it cannot.

Some rules in the standard resisted implementation entirely. “Avoid words that do not add information” and “do not use nominal phrases” require judgement about meaning, not pattern matching. We set those aside rather than approximate them badly. A rule that fires on the wrong things trains its user to ignore it.

What the tool knows

Beyond the rules themselves, LFWriteAssist draws on resources that already existed and were not being connected to each other: Diccionario Fácil, a dictionary of plain definitions maintained by Plena Inclusión Madrid; the EASIER corpus of simpler synonyms, built from 260 annotated documents covering 8,100 complex words; and acronym and abbreviation lists drawn from Wikilengua.

We added a few checks in Python that LanguageTool’s pattern language handles poorly (detecting over-long sentences and over-long words), plus a slider controlling how aggressively the text is summarised, with 100% preserving everything in the source.

The interface shows three panels: your text, the rules it triggered with explanations and definitions, and the corrected output with changes marked in green and open questions marked in orange. A side panel lets you switch individual rule categories on and off.

Who it is for

Worth being precise about this: LFWriteAssist is for the people who write Easy-to-Read, not the people who read it. That distinction matters, because it changes what a failure costs. If the tool mis-flags something, a trained adaptor notices and moves on. If we had aimed it at end users, the same error would reach the person it was meant to help.

It does not remove the validation step either. The UNE standard requires that readers with comprehension difficulties check the result, and nothing here changes that. What the tool can do is get the draft closer before it reaches them, so their time is spent on judgement rather than on catching mechanical rule breaks.

The code is open source. That was deliberate given Figure 1: building on a maintained platform and releasing the rules is the only version of this that has a chance of still working in five years.
